# Pending Features

This is an internal backlog for AI Data Compass. It is intentionally stored at the repository root because the content under `.ai-data-compass/docs/` is intended to be reusable by repositories that adopt AI Data Compass.

The tags below are stable references only. They are not priority levels or delivery order. Completed distribution/bootstrap and exportable-documentation work are omitted.

## Remaining work

| Tag | Pending feature | Description |
| --- | --- | --- |
| shared-completion-workflow | Shared completion workflow | The repository's “before considering a task done” process should be implemented as an explicit, repeatable workflow composed of skills and scripts. Each check should also remain usable independently during development.<br><br>The workflow should discover applicable project capabilities and invoke, as appropriate:<br>• code-test analysis and test execution;<br>• data-quality and business-rule checks;<br>• project-specific quality-metric collection and comparison;<br>• documentation consistency, link, and reference validation;<br>• documentation accuracy review;<br>• security and privacy checks;<br>• repository-specific assertions and integration tests.<br><br>The workflow must make its scope explicit, such as the whole repository, the current session, a branch, or a selected diff. It should produce concise, reviewable evidence for every check, distinguish skipped checks from passing checks, and fail or require explicit review when a required check cannot be completed. It must respect the project's privacy rules and avoid exposing sensitive data in reports or logs.<br><br>Current state: `AGENTS.md` defines the completion checklist; CI runs the Python and security-skill suites; `tests/test_distribution.py` checks Markdown links in the repository and in a temporary installation created by the CLI from the source tree. The reusable orchestrator is not implemented. |
| code-testing-skill | Language- and technology-agnostic code-testing skill | Create a skill that helps an LLM and a developer find and create missing code tests across different languages, frameworks, build systems, and execution environments. The skill must be language- and technology-agnostic in its orchestration and discovery process, but it must use the native testing capabilities of the technology being tested rather than reducing every project to generic language-level tests.<br><br>The skill should be usable in two scopes:<br>• the whole repository;<br>• only the current session's changes, branch changes, or another explicitly selected diff.<br><br>It should identify implemented functions or equivalent units of behavior that lack meaningful tests, and it should identify documented bugs that do not have regression tests. It must distinguish untestable infrastructure or generated code from genuine coverage gaps instead of producing a purely numerical coverage report.<br><br>The skill should discover and use the project's native test ecosystem and execution model, including applicable tools for Python, SQL, dbt, PySpark, Flink, Dataflow, pandas, and other data technologies. It should be extensible through technology-specific adapters or playbooks without changing the language-agnostic workflow.<br><br>The skill should support both workflows:<br>• invocation as part of the repository's “before considering a task done” procedure;<br>• standalone invocation to guide test creation during development.<br><br>This feature may include the unified validation entry point that runs the applicable repository tests and other deterministic checks. |
| data-quality-testing-skill | Data-quality and business-rule testing skill | Create a skill similar to the code-testing skill, but focused on data quality and business rules rather than application-code behavior. Like the code-testing skill, it must be language- and technology-agnostic at the orchestration level while using the full native capabilities of the project's data stack.<br><br>The initial scope should prioritize tests that are appropriate for the rule and execution environment. Row-level checks and uniqueness checks should be available where they are cheap and do not require an unnecessary distributed shuffle, but the skill must not impose a blanket restriction against using distributed or platform-native execution when that is the correct trade-off. The initial scope includes:<br>• row-level validity and required-field rules;<br>• type, range, format, and referential checks that can be evaluated locally;<br>• nullability and allowed-value rules;<br>• partition- or batch-level completeness checks where they do not require a full reshuffle;<br>• uniqueness tests and duplicate detection with explicitly documented cost, infrastructure, execution plan, and scope;<br>• business rules expressed as deterministic assertions.<br><br>The skill should support native approaches such as dbt tests and macros, PySpark or pandas test suites, Flink job or operator tests, Dataflow pipeline tests, SQL assertions, and framework-specific data-quality checks. It should select between local, sampled, partitioned, cluster, and full-scale execution based on the project's correctness needs and declared constraints.<br><br>For every proposed test, the skill should document the expected compute cost, required infrastructure, data volume, shuffle or network behavior, runtime, environment, and whether the test is suitable for local development, CI, staging, or production-like execution. It should use schemas, aggregates, synthetic fixtures, and metadata when possible, while respecting the project's privacy rules and avoiding unnecessary exposure of sensitive row values.<br><br>Tests should be independent of production systems when that is technically and operationally appropriate, but the skill must also support tests that require realistic infrastructure, representative data, managed services, or production-like execution when those are necessary to validate distributed behavior, query planning, performance, data contracts, or platform-specific semantics.<br><br>The skill should support both whole-repository and change-focused analysis and must make the selected scope and execution mode explicit in its output. |
| project-quality-metrics-skill | Project-specific quality-metrics skill | Create a skill that helps a project define the metrics it actually needs from the topic groups listed in `AGENTS.md`, rather than assuming every project must implement every metric.<br><br>The skill should:<br>• ask which topic groups are in scope;<br>• identify the owners, targets, thresholds, and review cadence;<br>• develop concrete metric definitions and collection procedures;<br>• distinguish required metrics from optional metrics;<br>• define how a baseline is created and how changes are compared with it;<br>• document expected cost, freshness, and failure behavior.<br><br>It must also help decide where and how metrics are stored, including a documented choice among options such as:<br>• CI artifacts or workflow summaries;<br>• files committed to the repository;<br>• a project database or metrics store;<br>• an external observability or governance system.<br><br>The selected storage mechanism must include retention, access, reproducibility, and privacy considerations.<br><br>Current state: no project quality-metric collection or baseline is configured. |
| documentation-validation-skills | Documentation validation and accuracy skills | Create two related skills for use in the “before considering a task done” procedure and as standalone development checks.<br><br>Documentation consistency and link validation should cover, as applicable:<br>• internal links and referenced files;<br>• required sections and headings;<br>• consistency between canonical agent guidance and model-specific adapters;<br>• references to commands, scripts, skills, and configuration paths;<br>• stale or unresolved placeholders in exportable assets;<br>• documentation changes required by changed interfaces or behavior.<br><br>It must report actionable metadata without printing sensitive file contents and should support repository-wide and change-focused scopes. Current state: distribution tests validate local Markdown links in the repository and packaged documentation; a reusable documentation-validation skill is not implemented.<br><br>A separate accuracy-review skill should review whether project documentation is accurate, complete, and consistent with the implementation and observed behavior. It should compare documentation with applicable repository evidence, including public interfaces, schemas, configuration, command-line options, source-code behavior and error handling, tests and fixtures, validation procedures, CI workflows, operational procedures, security/privacy/governance/classification requirements, examples, version statements, ownership, and compatibility claims.<br><br>It should identify claims that are stale, incomplete, ambiguous, unsupported, or contradicted by the implementation. It must distinguish a documentation gap from a possible implementation bug and recommend whether the code, the documentation, or both require a change.<br><br>The review must use safe evidence: schemas, metadata, synthetic fixtures, aggregates, command output, and source inspection. It must not require exposing sensitive or production row values. Findings should include the affected document, claim or section, supporting evidence type, confidence, and recommended action without copying sensitive content.<br><br>The skill should support whole-repository and change-focused reviews, and it should be able to run as part of the shared completion workflow. |
| complete-project-review-skill | Complete project review skill | Create a read-only skill for reviewing an entire repository as a senior reviewer. It must inspect code, tests, documentation, configuration, and operational workflows, and report only concrete issues classified by severity. It must not modify files.<br><br>For each finding, report the affected file and code section, a scenario that reproduces the issue, its impact, and the smallest suggested fix. Focus especially on regressions, error handling, concurrency, security, compatibility, performance, and missing tests. If no findings are identified, say so and list risks that could not be verified without running the system. Return results in a Markdown table by default, or JSON if the user requests it.<br><br>Use this English prompt as an initial example: “Review this repository as a senior reviewer. Do not modify any files. Report only concrete issues classified by severity. For each finding, provide the affected file and code section, a scenario that reproduces the issue, its impact, and the smallest suggested fix. Focus especially on regressions, error handling, concurrency, security, compatibility, performance, and missing tests. If you find no issues, say so and list risks that could not be verified without running the system. Format the results as a Markdown table, or as JSON if the user requests it.” |
| coding-harness-integrations | Model and coding-harness integrations | Integrate the canonical skills and reusable guidance with the models, coding agents, and execution harnesses used by the project. The repository should maintain one explicit compatibility matrix instead of referring to unnamed future adapters.<br><br>The compatibility scope identified so far is:<br>• Codex and Claude Code are the tested reference harnesses, with skill adapters and projection tests;<br>• instruction adapters also exist for Gemini, Cursor, Windsurf, and GitHub Copilot, but their full harness behavior has not been validated by the Codex and Claude tests;<br>• Gemini, Cursor, Windsurf, Kimi, GitHub Copilot, OpenCode, Grok, DeepSeek, and GLM remain targets for compatibility evaluation beyond the tested reference harnesses.<br><br>The existing GitHub Actions workflows and local CLI are part of the execution and automation surface. Current CI workflows run for pull requests, pushes to `main`, and manual dispatch; decide whether scheduled or release-specific runs are needed.<br><br>The integration design should keep one canonical implementation of each skill and use thin host-specific adapters where required. Each adapter should have a projection test that verifies discovery, loading, and version consistency without duplicating business logic.<br><br>The final supported-platform matrix, installation instructions, and known feature differences must be documented. |
| security-credential-patterns | Security audit: broader credential-pattern coverage | Expand detection beyond the current credential-shaped patterns to cover more provider-specific tokens, key formats, encoded values, multiline secrets, and secrets split across configuration structures.<br><br>Every new rule must document expected false positives, severity, confidence, and redaction behavior. Current rules also detect sensitive-looking filenames; the scanner does not verify whether a credential is active. |
| security-binary-archive-scanning | Security audit: binary, archive, and serialized-content scanning | Define a safe strategy for detecting credential candidates in binary, compressed, archived, serialized, and common data files, including formats such as SQLite, Parquet, Excel, PDF, and build artifacts where appropriate.<br><br>The implementation must set explicit size, recursion, decompression, and resource limits. Encrypted or unreadable content must be reported as an inspection limitation rather than treated as clean. |
| security-pii-phi-detection | Security audit: tool-assisted PII and PHI detection | Add an optional PII/PHI detection mode based on specialized tools or services, such as Presidio or comparable technology. The selected tools should support the project's required regulatory context, including HIPAA-related controls where applicable, without claiming that detection alone establishes compliance.<br><br>The mode must define supported entities, confidence thresholds, language coverage, false-positive handling, and metadata-only reporting. It must support schemas, aggregates, synthetic fixtures, or sampled data according to the repository's privacy rules rather than exposing raw records to the agent. |
| security-data-catalog-pii-phi | Security audit: Data-Catalog-driven PII and PHI detection | Add a second PII/PHI mode driven by the adopting project's own Data Catalog. The catalog should be able to declare classifications for datasets, tables, columns, fields, and rule-specific sensitivity categories.<br><br>The future catalog configuration interface should be able to:<br>• enable or disable catalog-driven checks;<br>• select the catalog source and version;<br>• configure sensitive fields and project-specific patterns;<br>• define applicable regulations and retention or access metadata;<br>• choose whether checks run locally, in CI, or against an approved metadata service;<br>• validate that the catalog configuration is complete and internally consistent.<br><br>The scanner must not infer that a field is safe merely because it is absent from the catalog. Unknown or unclassified fields should be reported according to an explicit project policy. |
| security-active-credential-verification | Security audit: optional active-credential verification | Define an opt-in workflow for confirming whether a finding is active, valid, or revocable through the owning provider.<br><br>This must never be part of the default offline scan. It requires explicit authorization, provider-specific credentials supplied outside repository content, audit logging, rate limits, and a policy for avoiding side effects. The default output must still avoid exposing the credential value. |
| security-working-tree-scope | Security audit: broader working-tree scope | The current scanner reads Git-tracked and nonignored untracked files. Provide an explicit mode for scanning ignored files, selected directories, or the complete filesystem scope supplied by the user, while keeping the current Git-aware mode as the safe default.<br><br>The implementation must define symlink handling, file-size limits, permission errors, excluded paths, and how inaccessible files are reported. |
| security-git-history-analysis | Security audit: more complete Git-history analysis | The current scanner analyzes commits reachable through `git rev-list --all`. Improve history coverage for sensitive filenames, renamed and deleted files, commit metadata where appropriate, and explicitly selected refs. Document the limits around unreachable objects, reflogs, stashes, Git LFS, and shallow or partial clones. |
| security-diagnostics-triage | Security audit: safe diagnostics and triage support | Improve the metadata-only report so maintainers can distinguish likely placeholders, examples, duplicates, and actionable findings without exposing matched values.<br><br>Possible metadata includes rule explanations, deterministic finding IDs, deduplication guidance, remediation links, and documented suppression or allowlist mechanisms. Any suppression must be reviewable and must not silently hide new findings. |
| security-error-completeness | Security audit: scanner error handling and completeness reporting | Ensure unreadable files, unsupported formats, skipped paths, truncation, and resource-limit events are reported explicitly. A scan must not present an incomplete inspection as a clean result.<br><br>Current behavior reports skipped non-regular files and finding-limit truncation; improve completeness details as the scanner gains formats and modes. |
| security-regression-tests | Security audit: test coverage | Current synthetic tests cover implemented rule families, working-tree and history modes, sensitive filenames in history, metadata-only redaction, truncation, JSON/Markdown output, and skipped non-regular files. Add regression tests for new detection and scan behavior, including binary/archive content, ignored files, expanded scope, PII/PHI modes, and catalog-driven checks.<br><br>Tests must never use real credentials, PII, or PHI. |
| security-ci-execution | Security audit: CI coverage and execution modes | Current workflows run for pull requests, pushes to `main`, and manual dispatch. Decide whether scheduled or release checks should be added, and specify their triggers and cadence.<br><br>The workflow must continue to obtain security-sensitive scanner logic from a trusted source, scan the candidate separately, and fail safely when the scan is incomplete or findings exceed configured limits. |
